# Plan 14 — any maker (2026-09-08)

Simon: "make it more generic about knives... I think the uptake is going to be across the brands... we might even think about a brand category." He is adding Hinderers and Striders next.

## Today
`knives.maker` is a *module key* and the registry has one module, `crk`. Every draft is created `maker='crk'`, every decode runs the CRK prompt + CRK ext schema, and there is no column for the brand name. A Hinderer added today files as a CRK with empty CRK fields.

## Design
1. **Core field `maker_name`** (free text, "as printed on the card, box or blade"). Joins `CORE_PROPS`, so it rides the schema, confidence, edit validation and `apply_decode` for free. DB column `knives.maker_name`, schema **v12**, backfilled `'Chris Reeve Knives'` where `maker='crk'`.
2. **Generic module `other`**: `EXT_PROPS = {}`, generic prompt, `flags()` → `[]`, `norm()` passthrough. Registry: `crk`, `other`.
3. **One decode, maker resolved after.** The prompt no longer assumes a maker: the base asks for `maker_name` from the card/box/tang stamp, then appends every registered module's `PROMPT` under "If the maker is X, apply:"; the schema's `ext` is the union of all modules' `EXT_PROPS` (today = CRK's). After the call, `makers.resolve(maker_name, card_text)` picks the module (CRK regex on brand/model names → `crk`, else `other`); `Decoded` gains `.maker`; `_to_decoded` takes ext for the resolved module only; `apply_decode` writes `knives.maker`. The `maker` argument to `decode()` becomes a fallback used only when the model returns an empty `maker_name`.
4. **Editing `maker_name`** re-resolves `maker`. Leaving `crk` clears `ext` (CRK-only values must not follow a knife re-filed as another brand).
5. **Display**: `maker_name` joins `PUBLIC_FIELDS`. `display_name()` prefixes the brand for non-CRK knives ("Hinderer Knives XM-18"); CRK names are unchanged. Knife page gets a "Maker" spec row. Register page (`html/me/index.html`) gets a `maker` field first in the form, the title prefixes the brand for non-CRK, and CRK-only `ext.*` rows are shown only for `maker === 'crk'` (so an `other` knife never posts ext keys). Add page card rows show maker.
6. **Search**: `search_cards.maker_name` column (migration 12 ALTERs it too — the table is in the main DB), `CARD_FIELDS` + `FTS_FIELDS` gain `maker_name`, aggregates gain `makers`, the search page shows the maker chips.
7. **Export**: CSV column `maker_name` after `maker`; register.html shows the brand.
8. **Tests**: v11→v12 migration test (the one owed since batch B), plus unit coverage per item.

Out of scope (noted for Simon): wants still key on module `maker` ('crk'); a want for "Hinderer" needs a `maker_name` want field — small follow-up. Eval script stays CRK-only.
